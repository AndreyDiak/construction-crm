# Решения, допущения и что не успели

## Решения там, где ТЗ не однозначно

1. **UI-библиотека: Chakra UI v3 вместо shadcn/ui.**  
   В проекте уже был Chakra; переход на shadcn потребовал бы Tailwind и переписывания всего UI без выигрыша для бизнес-логики и безопасности. Визуально довели до спокойного светлого SaaS-вида своей темой.

2. **Имена статусов в коде/БД.**  
   В требованиях: `in_review`, `needs_revision`. В текущей реализации: `on_review`, `needs_rework`. Смысл и переходы те же. Переименование запланировано отдельной миграцией, чтобы не ломать уже работающую базу и тесты одним коммитом.

3. **Архитектура FSD-lite.**  
   Слои `app / pages / features / entities / shared` сохранены без полной бюрократии FSD: нет обязательных публичных `index.ts` у всех модулей и глубокой вложенности `model/ui/lib`. Для размера приложения этого достаточно.

4. **Бизнес-правила статусов — только в PostgreSQL.**  
   Клиент показывает кнопки и вызывает RPC `transition_task_status`. Прямой `UPDATE` статуса запрещён грантами и триггером. Так нельзя обойти проверки через UI.

5. **Мягкое удаление объектов и задач.**  
   Физического `DELETE` нет: ставится `is_deleted = true`. История и аудит сохраняются; по удалённому объекту переходы статусов блокируются.

6. **Регистрация закрыта.**  
   Пользователей создаёт администратор. Новый профиль всегда стартует как исполнитель; роль постановщика выдаётся только SQL-ом в базе.

7. **Облачный Supabase + Vercel.**  
   Локальный Docker-стек для демо не обязателен: миграция одна, поднимается в SQL Editor. Фронт задеплоен на Vercel.

8. **Демо-данные.**  
   В облачной базе подготовлены 3 объекта и задачи во всех статусах, плюс 1 постановщик и 2 исполнителя.

## Что не успели / технический долг

1. Миграция имён статусов к каноническим из ТЗ (`in_review`, `needs_revision`).
2. Unit/component-тесты и CI-пайплайн (есть интеграционные security-тесты против реальной БД).
3. Типизированные ошибки и error boundary на фронте — ошибки сейчас через состояния экрана и toaster.
4. Публичные `index.ts` у модулей и автопроверка границ импортов.
5. SQL-тесты внутри `supabase/tests` — пока логика закрыта Node security-сьютом.

## Известные компромиссы

- Менеджер видит задачи на мягко удалённых объектах (исторический доступ), но переходы по ним запрещены.
- Чтобы мягко удалить задачу, объект должен быть активен; иначе сначала нужно восстановить объект, удалить задачи, снова удалить объект.
- Publishable-ключ фронта публичен по дизайну Supabase; защита — RLS и отсутствие секретов в клиенте.
