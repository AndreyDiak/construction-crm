# ADR-002: Server State Management

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Данные приложения хранятся в Supabase PostgreSQL и доступны через PostgREST/RPC. Клиент должен:

- загружать списки объектов и задач;
- загружать детали задачи и историю статусов;
- выполнять mutations (создание, редактирование, мягкое удаление, смена статуса);
- обновлять затронутые данные после mutations;
- не смешивать серверное состояние с локальным UI-состоянием;
- не выполнять запросы к Supabase из JSX-компонентов.

Дополнительно есть auth-состояние: сессия Supabase и профиль пользователя. Оно управляет маршрутизацией и должно реагировать на события Supabase Auth.

## Decision

Использовать TanStack Query как единый механизм работы с серверным состоянием.

- Все запросы к таблицам и RPC выполняются в API-функциях `src/features/<domain>/api.ts`.
- Query/mutation hooks размещаются в `src/features/<domain>/hooks.ts`.
- Query keys централизуются рядом с хуками в виде объектов `objectKeys`, `taskKeys`.
- Mutations выполняются через `useMutation`; инвалидация — в `onSuccess`.
- Ошибки mutations показываются через toaster в хуке; компонент не дублирует бизнес-сообщения.
- Локальное состояние (открытие диалога, выбранный элемент, поля формы) остаётся в React `useState`/React Hook Form.
- Данные TanStack Query не копируются в глобальный store.
- Auth-сессия и профиль остаются в `AuthProvider`, потому что они управляют жизненным циклом входа и маршрутизацией. Это осознанное исключение, а не общий способ хранения серверных данных.
- При выходе пользователя кэш TanStack Query должен очищаться.

Текущий `AuthProvider` загружает профиль прямым запросом к Supabase. Это допустимо как временное исключение, но логику следует вынести в API-функцию `features/auth/api.ts` или `entities/profile/api.ts` при следующем изменении auth-слоя.

## Rationale

- TanStack Query уже используется и хорошо подходит для инвалидации после mutations.
- Централизованные ключи уменьшают риск «забытых» обновлений.
- Разделение API-функций и hooks упрощает тестирование и повторное использование.
- Auth-состояние отличается от обычных запросов: оно должно реагировать на `onAuthStateChange`, влиять на guards и очищаться при logout.
- Запрет на копирование серверных данных в глобальный store предотвращает рассинхронизацию.

## Alternatives Considered

### Redux/Zustand для всего состояния

Отклонено: для серверного состояния это создаёт ручное управление кэшем, инвалидацией и загрузкой. Для локального UI-состояния достаточно React hooks.

### SWR

Отклонено: TanStack Query уже используется, имеет более развитые mutations и инструменты инвалидации. Смена библиотеки не даёт выгоды.

### Ручные fetch + `useEffect`

Отклонено: приводит к дублированию loading/error-состояний, гонкам и отсутствию кэша.

### Хранить профиль в TanStack Query как обычный запрос

Рассмотрено, но отклонено как обязательное решение: профиль тесно связан с auth-событиями и route guards. Допустимо вынести только API-функцию загрузки профиля, сохранив управление состоянием в `AuthProvider`.

## Consequences

Положительные:

- Единый подход к загрузке и инвалидации данных.
- Меньше ручного состояния и дублирования.
- Проще добавлять новые списки и mutations.
- Ошибки и загрузка обрабатываются единообразно.

Отрицательные:

- Требуется дисциплина ключей: неверный ключ или пропущенная инвалидация приводит к устаревшим данным.
- Текущая инвалидация в `invalidateTaskData` широкая: инвалидируются все задачи и объекты. Для малого приложения это безопасно, но неоптимально.
- Кэш TanStack Query не очищается при logout в текущей реализации. Это риск утечки ранее загруженных данных между пользователями.
- Auth-состояние живёт вне TanStack Query и требует отдельного внимания.

## Implementation Guidelines

### Query keys

Использовать префиксы по домену:

```ts
export const objectKeys = {
  all: ['objects'] as const,
  detail: (id: string) => ['objects', 'detail', id] as const,
}

export const taskKeys = {
  all: ['tasks'] as const,
  byObject: (objectId: string) => ['tasks', 'object', objectId] as const,
  my: (userId: string) => ['tasks', 'my', userId] as const,
  detail: (id: string) => ['tasks', 'detail', id] as const,
  history: (id: string) => ['tasks', 'history', id] as const,
  executors: ['profiles', 'executors'] as const,
}
```

Правила:

- Ключ списка должен включать все фильтры, влияющие на результат.
- Ключ, зависящий от пользователя, обязан включать `userId`.
- Не использовать пустые строки как «ключ по умолчанию» для detail-запросов; использовать `enabled: Boolean(id)` и отдельный `queryKey` без запроса.
- Не дублировать ключи в разных feature.

### Queries

- Query-функция не должна содержать UI-логику.
- Query-функция возвращает типизированную доменную модель, а не сырой ответ Supabase.
- Для необязательных параметров использовать `enabled`.
- Не выполнять запросы в JSX.
- Не использовать `useEffect` для вычисляемого состояния; вычислять его в рендере или в query-функции.

### Mutations

- Mutation-функция — тонкая обёртка над API-функцией.
- В `onSuccess` инвалидировать минимально достаточный набор ключей.
- В `onError` показывать пользовательское сообщение через `toaster` и `getErrorMessage`.
- Не делать optimistic update без явной необходимости и тестов на откат.
- Компонент может ловить ошибку `mutateAsync`, чтобы не было unhandled rejection, но не должен повторно показывать тот же toast.

### Auth-состояние

- `AuthProvider` отвечает за `getSession`, `onAuthStateChange`, загрузку профиля и `signOut`.
- При `signOut` необходимо очищать кэш: `queryClient.clear()` или удаление всех пользовательских ключей. Текущая реализация этого не делает; исправление обязательно при следующем изменении auth-flow.
- Не доверять `session.user.user_metadata.role`; роль читается из `profiles` и всё равно проверяется на сервере.
- Профиль загружать через API-функцию, а не напрямую из компонента.

### Локальное состояние

- Открытие/закрытие диалогов — `useState`.
- Поля форм — React Hook Form.
- Выбранный объект/задача — локальный `useState` страницы.
- Глобальный store для серверных данных не создавать.

### Настройки QueryClient

Текущие значения:

- `retry: 1`;
- `staleTime: 30_000`;
- `refetchOnWindowFocus: false`.

Менять их можно, но при изменении `staleTime` учитывать риск показа устаревших данных после смены пользователя. Очистка кэша при logout важнее, чем настройка `staleTime`.

## Validation

- Проверить, что в `pages` и `entities` нет прямых вызовов `supabase.from(...)`.
- Проверить, что каждый mutation инвалидирует связанные query keys.
- Проверить сценарий: вход executor1 → загрузка задач → выход → вход executor2. Данные executor1 не должны отображаться.
- Проверить, что после создания/редактирования/удаления задачи или объекта списки обновляются.
- Проверить, что ошибки mutation показываются один раз.
- Запустить `npm run typecheck` и `npm run lint`.
