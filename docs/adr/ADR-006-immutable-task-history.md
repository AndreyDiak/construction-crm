# ADR-006: Immutable Task History

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

История статусов задачи нужна для аудита, разбора спорных ситуаций и отображения комментариев при возврате на доработку. Если клиент сможет изменять или удалять историю, аудит перестанет быть достоверным.

Требуется:

- фиксировать каждое изменение статуса;
- фиксировать автора изменения и комментарий;
- запретить клиенту вставку, изменение и удаление истории;
- сохранять историю при мягком удалении задачи;
- не терять историю при удалении связанных сущностей;
- показывать историю manager и исполнителю доступной задачи.

## Decision

Таблица `public.task_status_history` является append-only журналом.

- Записи создаются только триггерами на `public.tasks`.
- Клиентский API имеет только `SELECT` на историю.
- Нет грантов и RLS-политик на `INSERT`, `UPDATE`, `DELETE`.
- История доступна manager и пользователю, который имеет доступ к задаче.
- `task_id` и `changed_by` ссылаются на `tasks` и `profiles` с `ON DELETE RESTRICT`.
- Мягкое удаление задачи или объекта не удаляет историю.
- Физическое удаление задач через клиентский API невозможно.
- Комментарий перехода `in_review → needs_revision` сохраняется в истории.
- Первая запись истории создаётся при создании задачи: `from_status = null`, `to_status = 'new'`.

## Rationale

- Триггеры — единственный способ гарантировать запись истории независимо от того, какой код меняет статус.
- Отсутствие грантов на запись делает историю неизменяемой для клиента даже при ошибке в RLS.
- `ON DELETE RESTRICT` защищает историю от каскадного удаления.
- Append-only модель проста и соответствует требованию аудита.
- Хранение комментария в истории позволяет показать причину возврата без отдельной таблицы комментариев.

## Alternatives Considered

### Писать историю из клиентского кода после успешного RPC

Отклонено: клиент может не выполнить запись, выполнить её повторно или подделать данные. История должна писаться в той же транзакции, что и изменение статуса.

### Разрешить клиенту `INSERT` истории с RLS-проверкой

Отклонено: увеличивает поверхность атаки и позволяет подделать `changed_by`, `from_status`, `to_status` или `comment`.

### Хранить историю в отдельном audit-сервисе

Отклонено: избыточно для мини-CRM. PostgreSQL-триггеры дают достаточный уровень аудита.

### Удалять историю вместе с задачей

Отклонено: противоречит требованию сохранять данные и уничтожает аудит.

### Разрешить редактирование комментария

Отклонено: история должна быть неизменяемой. Если нужны уточнения, добавлять новую запись, а не изменять старую.

## Consequences

Положительные:

- История всегда соответствует фактическим изменениям статуса.
- Клиент не может подделать или удалить аудит.
- Комментарии возврата на доработку сохраняются.
- Мягкое удаление не уничтожает историю.

Отрицательные:

- Нельзя исправить ошибочный комментарий задним числом.
- История растёт вместе с количеством переходов; нужен индекс по `task_id, created_at`.
- Триггеры добавляют неявную логику; их изменение требует миграции и тестов.
- `ON DELETE RESTRICT` усложняет удаление пользователей и задач; физическое удаление должно выполняться осознанно администратором.
- Владелец БД технически может изменить историю; модель защищает клиентский API, а не администратора БД.

## Implementation Guidelines

### Схема

```sql
create table public.task_status_history (
  id uuid primary key default gen_random_uuid(),
  task_id uuid not null references public.tasks (id) on delete restrict,
  changed_by uuid not null references public.profiles (id) on delete restrict,
  from_status public.task_status,
  to_status public.task_status not null,
  comment text check (comment is null or char_length(comment) <= 2000),
  created_at timestamptz not null default now()
);

create index task_history_task_created_idx
  on public.task_status_history (task_id, created_at);
```

Канонические имена статусов и текущее расхождение описаны в [ADR-005](./ADR-005-task-status-workflow.md).

### Триггеры

- `log_task_status_history_after_insert` — создаёт начальную запись при вставке задачи.
- `log_task_status_history_after_status_update` — создаёт запись только при изменении `status`.

Правила:

- `changed_by` берётся из `auth.uid()`, fallback — `author_id` задачи.
- Комментарий берётся из transaction-local GUC `crm.transition_comment`, который устанавливает RPC.
- Триггеры должны быть `SECURITY DEFINER` с `set search_path = public, pg_temp`, чтобы писать в историю независимо от прав вызывающего.
- Не добавлять триггеры, которые пишут историю при изменении не-статусных полей.
- Не логировать `updated_at` и другие служебные изменения как статусные переходы.

### Права

- `grant select on public.task_status_history to authenticated`.
- Не выдавать `insert`, `update`, `delete` ролям `anon` и `authenticated`.
- Не создавать RLS-политики на запись.
- Не отключать RLS на таблице истории.

### Чтение

- Manager видит историю всех задач.
- Executor видит историю только доступных ему задач.
- Запрос истории выполняется в `features/tasks/api.ts` (`getTaskHistory`).
- UI показывает `from_status`, `to_status`, `changed_by`, `comment`, `created_at`.
- Для первой записи `from_status = null` отображается как «Создание».

### Мягкое удаление

- `tasks.is_deleted = true` скрывает задачу от executor, но manager продолжает видеть историю.
- `objects.is_deleted = true` скрывает задачи и историю от executor; manager видит исторические строки.
- Не удалять строки истории при soft delete.
- Не добавлять каскадное удаление истории.

### Ограничения аудита

История фиксирует только статусные переходы. Она не является полным audit log и не содержит:

- IP-адрес;
- user agent;
- изменения не-статусных полей;
- удаление/восстановление;
- причины изменения assignee.

Если потребуется полный аудит, это должно быть отдельным решением и, вероятно, отдельной таблицей.

## Validation

- Проверить, что при создании задачи появляется ровно одна начальная запись.
- Проверить, что каждый успешный переход добавляет ровно одну запись.
- Проверить, что неуспешный переход не добавляет запись.
- Проверить, что executor не может вставить/изменить/удалить историю.
- Проверить, что manager не может вставить/изменить/удалить историю через клиентский API.
- Проверить, что комментарий возврата на доработку сохранён и совпадает с введённым.
- Проверить, что soft delete задачи/объекта не удаляет историю.
- Проверить, что executor не видит историю чужой задачи.
- Запустить `npm run test:security` при наличии тестового окружения.
