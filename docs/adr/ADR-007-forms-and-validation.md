# ADR-007: Forms and Validation

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

В приложении есть формы:

- вход (`LoginForm`);
- создание/редактирование объекта (`ObjectFormDialog`);
- создание/редактирование задачи (`TaskFormDialog`);
- комментарий при возврате задачи на доработку (`TaskActions`).

Формы должны:

- давать быструю обратную связь пользователю;
- не дублировать бизнес-логику, которая уже есть в PostgreSQL;
- корректно отображать серверные ошибки;
- не выполнять запросы к Supabase напрямую;
- использовать единый стек React Hook Form + Zod.

Ограничения БД уже задают длину полей, обязательность, роли, переходы и права. Клиентская валидация не заменяет серверную.

## Decision

Использовать React Hook Form + Zod для всех форм.

- Схемы размещаются в `src/features/<domain>/<name>.schema.ts`.
- Тип значений формы выводится из схемы: `z.infer<typeof schema>`.
- Подключение схемы — через `zodResolver`.
- Клиентская схема повторяет пользовательские ограничения (обязательность, длина, формат), но источник истины — PostgreSQL constraints, RLS и RPC.
- Ошибки полей отображаются через `Field.ErrorText`.
- Серверные ошибки показываются через общий обработчик `getErrorMessage` и toaster/Alert.
- Формы вызывают feature-хуки mutations, а не Supabase напрямую.
- После успешной mutation диалог закрывается, списки инвалидируются хуком.
- Комментарий при возврате на доработку валидируется и на клиенте, и в RPC.

Текущая схема использует локальную Zod-схему внутри `TaskActions.tsx`. Это допустимо, но при следующем изменении её следует вынести в `src/features/tasks/comment.schema.ts` для единообразия.

## Rationale

- React Hook Form и Zod уже используются; смена стека не даёт выгоды.
- Zod-схемы дают типобезопасные значения и единый способ отображения ошибок.
- Клиентская валидация улучшает UX, но не создаёт ложного ощущения безопасности, если серверные ограничения остаются обязательными.
- Feature-хуки скрывают детали API и инвалидации от форм.
- Общий обработчик ошибок предотвращает утечку технических сообщений Supabase в UI.

## Alternatives Considered

### Валидация только на сервере

Отклонено: плохой UX и лишние сетевые запросы, хотя безопасность остаётся на сервере.

### Валидация только на клиенте

Отклонено: легко обходится; не заменяет constraints, RLS и RPC.

### Formik

Отклонено: проект уже использует React Hook Form; смена библиотеки не требуется.

### Отдельная библиотека схем (Yup, Valibot)

Отклонено: Zod уже используется и связан с TypeScript. Добавление второй схемной библиотеки не нужно.

### Генерировать клиентские схемы из БД

Рассмотрено как будущее улучшение. Сейчас схемы пишутся вручную; при изменении constraints нужно синхронизировать их с ADR-004 и миграцией.

## Consequences

Положительные:

- Единый подход к формам и ошибкам.
- Типобезопасные значения форм.
- Хорошая интеграция с Chakra UI.
- Серверные ограничения остаются источником истины.

Отрицательные:

- Ограничения длины дублируются в Zod и БД; нужно синхронизировать.
- Серверные ошибки могут быть менее точными, чем клиентские.
- Локальная схема комментария в `TaskActions.tsx` нарушает единообразие размещения.
- `useEffect` для `reset` при открытии диалога является исключением из правила «не использовать useEffect для вычисляемого состояния»; это синхронизация с внешним `open`, а не вычисление.

## Implementation Guidelines

### Схемы

Текущие файлы:

- `src/features/auth/login.schema.ts`;
- `src/features/objects/object-form.schema.ts`;
- `src/features/tasks/task-form.schema.ts`;
- локальная `commentSchema` в `src/features/tasks/TaskActions.tsx`.

Правила:

- Все строковые поля, которые обрезаются в БД, должны использовать `.trim()`.
- Обязательные поля — `.min(1, '...')`.
- Максимальные длины должны совпадать с constraints БД.
- Для необязательного описания использовать `optional()` или `nullable()` осознанно; API-функция должна приводить пустую строку к `null`.
- Сообщения об ошибках — на русском, понятные пользователю.
- Не включать в схему бизнес-правила, которые зависят от роли или состояния задачи; их проверяет сервер.
- Для комментария возврата на доработку минимум 1 символ после `trim`, максимум 2000.

### Формы

- Использовать `useForm<TValues>({ resolver: zodResolver(schema), defaultValues })`.
- Ошибки полей: `formState.errors.<field>?.message`.
- Отключать submit, если mutation уже выполняется.
- Показывать серверную ошибку в `Alert` или через toaster.
- Не выполнять `supabase`-запросы в обработчике формы; вызывать mutation hook.
- При успехе закрывать диалог и не показывать дублирующий toast, если хук уже показывает его.
- При ошибке не закрывать диалог, чтобы пользователь мог исправить данные.

### Сброс формы

Текущий подход — `useEffect` на `open`/`object`/`task` с `reset(...)`. Это допустимо для синхронизации формы с открытием диалога.

Предпочтительная альтернатива при рефакторинге — монтировать форму по `key` при каждом открытии, чтобы не использовать эффект. Не менять поведение без тестов.

### Ошибки

- Клиентские ошибки Zod показываются у полей.
- Ошибки Supabase/PostgREST обрабатываются через `getErrorMessage`.
- Не показывать пользователю сырые SQL-сообщения, коды и stack trace.
- Ошибки auth показывать в `LoginForm` через `Alert`.
- Ошибки загрузки исполнителей показывать в `TaskFormDialog` и блокировать submit, если исполнителей нет.

### Согласование с БД

При изменении constraints в миграции:

1. Обновить Zod-схему.
2. Обновить `database.types.ts`, если изменились типы.
3. Обновить UI-подсказки и сообщения.
4. Добавить или обновить тест на граничное значение.

## Validation

- Проверить, что пустые обязательные поля не отправляются.
- Проверить, что превышение длины отклоняется клиентом и БД.
- Проверить, что пустое описание сохраняется как `null`.
- Проверить, что комментарий возврата на доработку обязателен.
- Проверить, что серверная ошибка отображается и не теряется.
- Проверить, что формы не вызывают Supabase напрямую.
- Проверить, что после успешной mutation списки/детали обновляются.
- Запустить `npm run typecheck` и `npm run lint`.
