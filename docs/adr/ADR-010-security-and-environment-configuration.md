# ADR-010: Security and Environment Configuration

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Frontend использует Supabase publishable key, который по определению попадает в клиентский бандл. Безопасность не может строиться на сокрытии этого ключа: её обеспечивают RLS, гранты, RPC и правильная настройка Auth.

При этом секретные ключи (`sb_secret_...`, ранее `service_role`) не должны попадать во frontend. Vite встраивает все переменные с префиксом `VITE_` в бандл, поэтому ошибка в наименовании переменной может привести к утечке.

Требуется зафиксировать:

- какие переменные окружения используются;
- какие ключи публичные, а какие секретные;
- как защищаются SQL-функции и миграции;
- как выполняется развёртывание;
- как проверять отсутствие утечек.

## Decision

### Переменные окружения

Frontend использует только:

```env
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Тестовое окружение дополнительно использует:

```env
TEST_MANAGER_EMAIL=...
TEST_MANAGER_PASSWORD=...
TEST_EXECUTOR_EMAIL=...
TEST_EXECUTOR_PASSWORD=...
TEST_EXECUTOR_2_EMAIL=...
TEST_EXECUTOR_2_PASSWORD=...
```

Правила:

- `.env.local`, `.env.test`, `.env.test.local` не коммитятся.
- В репозитории хранятся только `.env.example` и `.env.test.example` с заполнителями.
- `VITE_SUPABASE_PUBLISHABLE_KEY` содержит только publishable key.
- `sb_secret_...`/`service_role` запрещены в любых `VITE_`-переменных.
- `service_role` не используется во frontend вообще.
- Publishable key считается публичным; безопасность обеспечивается RLS.
- Для dev/staging/prod используются разные Supabase-проекты и разные ключи.
- При подозрении на утечку секретного ключа его нужно перевыпустить, а `dist` удалить и пересобрать.

### Проверки при сборке

Текущие проверки:

- `src/shared/api/supabase.ts` выбрасывает ошибку, если не заданы `VITE_SUPABASE_URL` или `VITE_SUPABASE_PUBLISHABLE_KEY`.
- `src/shared/api/supabase.ts` выбрасывает ошибку, если publishable key начинается с `sb_secret_`.
- `vite.config.ts` проверяет все `VITE_`-переменные и выбрасывает ошибку при `sb_secret_`.
- `.gitignore` исключает локальные env-файлы.

Эти проверки обязательны и не должны ослабляться.

### Миграции и SQL-привилегии

- Схема, RLS, триггеры и RPC применяются только через миграции в `supabase/migrations/`.
- Миграции выполняются владельцем БД (`postgres`) в Supabase.
- `SECURITY DEFINER`-функции обязаны иметь `set search_path = public, pg_temp`.
- `EXECUTE` на служебные функции отзывается у `public` и `anon`; нужные функции выдаются `authenticated`.
- Клиентские гранты выдаются только на необходимые таблицы и колонки.
- `ALTER DEFAULT PRIVILEGES` отзывает автоматические права у `anon` и `authenticated` для новых объектов.
- RLS включается и принудительно (`FORCE ROW LEVEL SECURITY`) для таблиц с пользовательскими данными.
- Не отключать RLS и не ослаблять политики ради исправления ошибок.

### Auth

- Самостоятельная регистрация отключена в Supabase Dashboard.
- Пользователи создаются администратором.
- Email должен быть подтверждён.
- Пароли не хранятся и не логируются приложением.
- Роль хранится в `profiles` и не редактируется клиентом.
- Парольная политика и rate limits настраиваются в Supabase Auth.

### Развёртывание

Порядок:

1. Применить миграции к целевому проекту.
2. Проверить RLS и гранты (security-тесты).
3. Собрать frontend с publishable key целевого проекта.
4. Задеплоить статические assets.
5. Проверить вход, роли и базовые сценарии.

Правила:

- Не деплоить frontend, который ожидает новую схему, до применения миграции.
- Не применять разрушительные миграции без резервной копии.
- Не использовать production-проект для integration-тестов.
- Секреты CI хранить в secret storage, не в репозитории.
- Сборка не должна содержать `sb_secret_`, `service_role` или тестовые пароли.

## Rationale

- Publishable key не является секретом; RLS — реальная граница безопасности.
- Запрет секретов в `VITE_` предотвращает наиболее вероятный сценарий утечки.
- Проверки на этапе сборки дешевле, чем реагирование на инцидент.
- `SECURITY DEFINER` с фиксированным `search_path` защищает от подмены схемы.
- Явные гранты и `ALTER DEFAULT PRIVILEGES` уменьшают риск случайного открытия новых таблиц.
- Разделение окружений снижает риск тестовых данных и ключей в production.

## Alternatives Considered

### Использовать `service_role` на клиенте для упрощения запросов

Запрещено. Полный доступ в обход RLS; утечка ключа означает компрометацию всей БД.

### Хранить publishable key в секрете

Не имеет смысла: ключ всё равно попадает в бандл. Безопасность должна обеспечиваться RLS.

### Отключить RLS и проверять доступ только в приложении

Запрещено. Прямой доступ к PostgREST обойдёт проверки.

### Применять миграции вручную в SQL Editor без версионирования

Допустимо только как аварийная процедура для начального прототипа; в дальнейшем — только версионированные миграции. Ручные изменения приводят к drift.

### Хранить env-файлы в репозитории

Запрещено. В репозитории только примеры.

## Consequences

Положительные:

- Секретные ключи не попадают в frontend.
- RLS и гранты остаются основным барьером.
- Сборка падает при явной утечке секрета в `VITE_`.
- Есть предсказуемый порядок деплоя.
- Новые объекты БД не открываются автоматически.

Отрицательные:

- Требуется ручное управление пользователями и ролями в Supabase.
- Проверки env не заменяют аудит бандла; нужна дополнительная проверка в CI.
- Разделение окружений увеличивает количество конфигураций.
- Ошибки в миграциях могут заблокировать деплой; нужна дисциплина и backup.

## Implementation Guidelines

### Env-файлы

- `.env.example` — только публичные переменные.
- `.env.test.example` — публичные переменные и тестовые пользователи.
- `.env.local` — локальная разработка, не коммитить.
- `.env.test` — тестовое окружение, не коммитить.
- Не добавлять `VITE_SUPABASE_SERVICE_ROLE_KEY`, `VITE_SUPABASE_SECRET_KEY` и аналогичные переменные.

### Проверка бандла

Перед деплоем:

```bash
npm run build
```

Затем проверить, что в `dist` нет:

- `sb_secret_`;
- `service_role`;
- тестовых паролей;
- `.env.test`.

Поиск можно выполнять локально или в CI. Если секрет найден — удалить `dist`, перевыпустить ключ и повторить сборку.

### Миграции

- Не редактировать применённые миграции.
- Для изменений создавать новую миграцию с timestamp.
- Проверять `supabase db diff`/`supabase db push` на тестовом проекте.
- Для `SECURITY DEFINER` всегда указывать `search_path`.
- Для новых функций: `revoke all ... from public, anon` и точечный `grant execute`.
- Для новых таблиц: RLS, `FORCE RLS`, политики, гранты, индексы.
- Не выдавать `ALL` ролям `anon`/`authenticated`.

### Supabase Auth

В Dashboard проверить:

- Email signups отключены.
- Email confirmations включены.
- Парольная политика соответствует требованиям.
- Rate limits настроены.
- Тестовые пользователи не используются в production.

### CI

- Секреты не печатать в логах.
- Integration-тесты запускать только с тестовым проектом.
- Проверять typecheck, lint, build.
- По возможности сканировать `dist` на секреты.
- Не запускать destructive-миграции автоматически на production.

## Validation

- Проверить, что `VITE_SUPABASE_PUBLISHABLE_KEY` начинается с `sb_publishable_`.
- Проверить, что `sb_secret_` отсутствует в `dist` и в env-файлах с префиксом `VITE_`.
- Проверить, что `service_role` не используется в `src`.
- Проверить, что `.env.local` и `.env.test` игнорируются git.
- Проверить, что RLS включён и форсирован для всех таблиц.
- Проверить, что `SECURITY DEFINER`-функции имеют `search_path`.
- Проверить, что `anon` не имеет доступа к таблицам и RPC.
- Проверить, что новые таблицы/функции не получают права автоматически.
- Запустить security-тесты на тестовом проекте.
