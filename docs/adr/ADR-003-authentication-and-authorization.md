# ADR-003: Authentication and Authorization

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Приложение использует Supabase Auth и две роли:

- `manager` — создаёт и управляет объектами и задачами, назначает исполнителей, принимает задачи и возвращает их на доработку;
- `executor` — видит только свои задачи и связанные объекты, выполняет задачи и отправляет их на проверку.

Требуется разграничить ответственность frontend и backend. Клиентские проверки ролей нужны для UX, но не могут быть источником безопасности: пользователь может изменить JavaScript, запросы и локальное состояние. Реальная авторизация должна выполняться в PostgreSQL через RLS и RPC.

Дополнительно требуется исключить самостоятельную регистрацию и повышение роли через клиентский API.

## Decision

Использовать Supabase Auth с email/password и профилем в таблице `public.profiles`.

- Регистрация отключена в Supabase Dashboard. Пользователей создаёт администратор.
- При создании пользователя триггер `handle_new_user` создаёт профиль с ролью `executor`.
- Роль `manager` выдаётся только администратором БД через SQL; клиентский API не может изменить `profiles.role`.
- `manager` и `executor` определяются по `profiles.role`, а не по `user_metadata` и не по данным, переданным клиентом.
- Frontend использует роль только для отображения и маршрутизации. Все ограничения доступа обеспечиваются RLS и RPC.
- Защищённые маршруты оборачиваются в `ProtectedRoute`, который проверяет наличие сессии и профиля.
- `HomeRedirect` направляет `manager` на `/objects`, а `executor` на `/my-tasks`.
- Прямые маршруты к объектам и задачам доступны обеим ролям; RLS скрывает недоступные строки.
- Выход из системы должен очищать кэш TanStack Query, чтобы данные предыдущего пользователя не отображались новому.
- `service_role` и секретные ключи Supabase не используются во frontend.

Текущая реализация не имеет отдельного role-based route guard: `/my-tasks` для manager показывает заглушку, а `/objects` доступен обеим ролям. Это допустимо для безопасности, потому что RLS фильтрует данные, но требует улучшения UX. Добавление role guard считается точечным улучшением, а не сменой модели авторизации.

## Rationale

- Supabase Auth уже интегрирован и поддерживает refresh session.
- RLS — единственный надёжный барьер для пользовательских запросов через publishable key.
- Профиль в отдельной таблице позволяет хранить роль и отображаемое имя, не затрагивая `auth.users`.
- Запрет регистрации и редактирования роли исключает самостоятельное повышение привилегий.
- Проверка роли на клиенте улучшает UX, но не создаёт ложного чувства безопасности, если явно задокументирована как неавторитетная.

## Alternatives Considered

### Собственный backend с JWT и проверкой ролей

Отклонено: избыточно для мини-CRM и дублирует Supabase Auth/PostgREST.

### Роль в `user_metadata` или custom JWT claims

Отклонено: metadata может быть изменена клиентом в зависимости от настроек; claims требуют дополнительной синхронизации. Роль в `profiles` с RLS и защитой от записи проще и надёжнее.

### Только клиентские проверки ролей

Отклонено: не обеспечивает безопасность. Любой пользователь может вызвать API напрямую.

### Самостоятельная регистрация с выбором роли

Отклонено: позволяет создать manager без участия администратора.

### Отдельный role guard для каждого маршрута

Пока не внедрён. Может быть добавлен для UX, но не заменяет RLS.

## Consequences

Положительные:

- Роли и доступ проверяются на сервере.
- Невозможно повысить роль через клиентский API.
- Регистрация закрыта, новые пользователи контролируются администратором.
- Один источник истины для роли — `profiles.role`.

Отрицательные:

- Управление пользователями и ролями выполняется вручную через Supabase Dashboard/SQL.
- Профиль загружается отдельным запросом после установки сессии; при ошибке нужен явный экран.
- Нет автоматического role guard на уровне маршрутов; UX зависит от условного рендера.
- После logout кэш запросов должен очищаться вручную; текущая реализация требует доработки.
- Все authenticated-пользователи могут читать `profiles` (имя и роль) — это осознанная уступка для отображения исполнителей и истории.

## Implementation Guidelines

### Auth-слой

Файлы:

- `src/features/auth/api.ts` — `signInWithPassword`, `signOut`;
- `src/features/auth/AuthProvider.tsx` — сессия, профиль, подписка на `onAuthStateChange`;
- `src/features/auth/auth-context.ts` — `AuthContextValue` и `useAuth`;
- `src/features/auth/LoginForm.tsx` — форма входа;
- `src/features/auth/login.schema.ts` — Zod-схема.

Правила:

- Не помещать роль в `localStorage`, `sessionStorage` или URL.
- Не доверять `session.user.user_metadata.role`.
- При загрузке профиля использовать `profiles` и проверять, что запись существует.
- При отсутствии профиля показывать экран ошибки и возможность выйти.
- При `signOut` очищать сессию, профиль и кэш запросов.

### Route guards

Текущая схема:

```text
/login          — публичный
/               — ProtectedRoute → HomeRedirect
/objects        — ProtectedRoute → AppLayout
/objects/:id    — ProtectedRoute → AppLayout
/tasks/:id      — ProtectedRoute → AppLayout
/my-tasks       — ProtectedRoute → AppLayout
*               — NotFoundPage
```

Правила:

- `ProtectedRoute` проверяет только сессию и профиль; не должен содержать доменные проверки.
- Роль используется для редиректа и условного отображения действий.
- Если добавляется role guard, он должен быть UX-ограничением, а не заменой RLS.
- Недоступные объекты и задачи должны отображаться как «не найдено/недоступно», а не раскрывать существование чужих записей.

### Матрица возможностей

`manager`:

- читает все объекты и задачи;
- создаёт/редактирует/мягко удаляет объекты;
- создаёт/редактирует/мягко удаляет задачи;
- назначает исполнителя;
- принимает задачи и возвращает на доработку с комментарием;
- видит историю статусов.

`executor`:

- читает только назначенные ему активные задачи и связанные активные объекты;
- переводит свои задачи `new → in_progress`, `in_progress → in_review`, `needs_revision → in_progress`;
- не создаёт и не редактирует объекты/задачи;
- не принимает и не возвращает задачи;
- видит историю своих задач.

### Создание пользователей и ролей

1. Создать пользователя в Supabase Dashboard.
2. Триггер создаст профиль с ролью `executor`.
3. Назначить manager только через SQL администратора:

```sql
update public.profiles p
set role = 'manager'
from auth.users u
where p.id = u.id
  and u.email = 'manager@example.com';
```

Клиентский API не должен иметь возможности выполнить этот update.

### Защита от обхода

- Не отключать RLS ради исправления ошибок.
- Не добавлять `service_role` во frontend.
- Не передавать `user_id` или `role` из клиента как основание для доступа.
- RPC должен самостоятельно получать `auth.uid()` и проверять роль в БД.
- UI-проверки не считать границей безопасности.

## Validation

- Проверить, что executor не видит чужие задачи и объекты через прямой запрос.
- Проверить, что executor не может создать объект/задачу или изменить статус напрямую.
- Проверить, что manager видит все объекты, задачи и историю.
- Проверить, что role escalation через `profiles` запрещён.
- Проверить, что анонимный пользователь не имеет доступа.
- Проверить сценарий logout → login другим пользователем: кэш не должен содержать данные предыдущего пользователя.
- Запустить `npm run test:security` при наличии `.env.test`.
