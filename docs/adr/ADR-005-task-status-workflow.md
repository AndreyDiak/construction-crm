# ADR-005: Task Status Workflow

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Статус задачи — ключевая часть бизнес-логики. Нельзя допустить, чтобы клиент напрямую менял `tasks.status` или выполнял переходы, не соответствующие роли и текущему состоянию задачи.

Требования определяют пять статусов:

- `new`
- `in_progress`
- `in_review`
- `accepted`
- `needs_revision`

Разрешённые переходы:

- `new → in_progress`
- `in_progress → in_review`
- `in_review → accepted`
- `in_review → needs_revision` (обязателен комментарий)
- `needs_revision → in_progress`

Текущая реализация использует другие имена для двух статусов:

- `on_review` вместо `in_review`;
- `needs_rework` вместо `needs_revision`.

Семантика и граф переходов совпадают. Это решение фиксирует канонические имена из требований и признаёт текущую реализацию отклонением, которое нужно устранить отдельной миграцией. Код и БД в рамках создания документации не меняются.

## Decision

Каноническая машина состояний задачи:

| Из | В | Кто | Дополнительно |
|---|---|---|---|
| `new` | `in_progress` | назначенный executor | — |
| `in_progress` | `in_review` | назначенный executor | — |
| `in_review` | `accepted` | manager | — |
| `in_review` | `needs_revision` | manager | комментарий обязателен |
| `needs_revision` | `in_progress` | назначенный executor | — |

`accepted` — конечный статус. Из него нет переходов.

Смена статуса выполняется только через RPC `public.transition_task_status`. Прямой `UPDATE tasks SET status = ...` запрещён на уровне грантов и триггера.

RPC должен быть атомарным, блокировать строку задачи на время проверки и изменения, проверять роль, назначение, текущий статус, допустимость перехода, комментарий и активность объекта. История пишется триггером в той же транзакции.

До миграции имён текущая БД и код используют `on_review` и `needs_rework`. Маппинг:

| Канон | Текущая реализация |
|---|---|
| `in_review` | `on_review` |
| `needs_revision` | `needs_rework` |

## Rationale

- Серверная проверка перехода — единственный способ гарантировать бизнес-правила при прямом доступе к PostgREST.
- `FOR UPDATE` предотвращает гонку двух одновременных переходов.
- `SECURITY DEFINER` RPC позволяет централизованно проверить роль и назначение, не выдавая клиенту лишние права на таблицу.
- Триггер `protect_task_status` создаёт второй барьер: даже при ошибке в грантах прямой `UPDATE status` будет отклонён.
- Комментарий при возврате на доработку хранится в истории и доступен исполнителю.
- Канонические имена из требований устраняют неоднозначность в документации, тестах и будущем API.

## Alternatives Considered

### Разрешить прямой `UPDATE status` с проверкой в RLS

Отклонено: RLS проверяет доступ к строке, но не выражает граф переходов и роль актора. Логика стала бы нечитаемой и хрупкой.

### Проверять переходы только на клиенте

Отклонено: легко обходится прямым запросом к Supabase.

### Триггер вместо RPC

Рассмотрено. Триггер может проверить переход, но RPC даёт явный контракт, возвращает обновлённую задачу и позволяет централизованно управлять правами на выполнение. Триггер оставлен как дополнительная защита.

### Универсальный RPC `update_task` с полем `status`

Отклонено: смешивает редактирование полей и смену статуса, усложняет проверки и повышает риск обхода.

### Оставить текущие имена `on_review`/`needs_rework`

Отклонено на уровне архитектурного решения: требования тестового задания являются источником истины. Текущие имена сохраняются только до миграции.

## Consequences

Положительные:

- Все переходы проверяются в одном месте.
- Невозможно обойти правила через прямой `UPDATE`.
- Комментарий при доработке гарантированно сохраняется.
- Конкурентные переходы сериализуются блокировкой строки.
- История всегда соответствует фактическому изменению статуса.

Отрицательные:

- Требуется миграция имён статусов в enum, RPC, типах, UI и тестах.
- RPC содержит бизнес-логику на PL/pgSQL; её сложнее тестировать, чем чистую функцию TypeScript.
- Ошибки RPC нужно маппить в понятные сообщения UI.
- Клиентская UI-модель переходов должна синхронизироваться с серверной, но не является источником истины.
- При добавлении новых статусов потребуется менять enum, RPC, UI и тесты.

## Implementation Guidelines

### Контракт RPC

```sql
public.transition_task_status(
  p_task_id uuid,
  p_to_status public.task_status,
  p_comment text default null
) returns public.tasks
```

Порядок проверок:

1. `auth.uid()` не `null`, иначе `42501`.
2. Профиль пользователя существует, иначе `42501`.
3. Задача читается с `FOR UPDATE`; если не найдена — `P0002`.
4. Задача не удалена, иначе `23514`.
5. Объект задачи активен, иначе `23514`.
6. Для executor: задача назначена ему, иначе `42501`; переход входит в разрешённый набор.
7. Для manager: переход `in_review → accepted` или `in_review → needs_revision`.
8. Для `in_review → needs_revision` комментарий обязателен, иначе `23514`.
9. Установить transaction-local GUC:
   - `crm.allow_status_transition = 'on'`;
   - `crm.transition_comment = <comment>`.
10. Обновить `tasks.status`.
11. Триггер `protect_task_status` пропускает изменение.
12. Триггер `log_task_status_history` пишет запись.
13. Вернуть обновлённую строку.

### Защита от обхода

- RPC должен быть `SECURITY DEFINER` с `set search_path = public, pg_temp`.
- `revoke all on function ... from public, anon`; `grant execute ... to authenticated`.
- `protect_task_status` должен отклонять любое изменение `status`, если GUC не установлен.
- GUC устанавливается только внутри RPC и только на текущую транзакцию; клиент не должен иметь возможности выставить его через PostgREST.
- Не выдавать `UPDATE (status)` клиенту.
- Не добавлять альтернативный RPC, который меняет статус без тех же проверок.
- Не принимать `user_id`, `role` или `assignee_id` как доказательство доступа.

### Текущая реализация

Файлы и объекты:

- `supabase/migrations/20261104000000_init.sql` — enum, RPC, триггеры;
- `src/features/tasks/api.ts` — `transitionTaskStatus` вызывает RPC;
- `src/features/tasks/hooks.ts` — `useTransitionTask`;
- `src/features/tasks/TaskActions.tsx` — кнопки доступных переходов и диалог комментария;
- `src/shared/lib/task-status.ts` — UI-метаданные и `getAvailableTransitions`;
- `src/shared/api/database.types.ts` — `TaskStatus`.

Сейчас эти файлы используют `on_review` и `needs_rework`.

### План миграции имён (не выполнен)

1. Создать новую миграцию.
2. Переименовать значения enum:
   - `alter type public.task_status rename value 'on_review' to 'in_review';`
   - `alter type public.task_status rename value 'needs_rework' to 'needs_revision';`
3. Обновить литералы в `transition_task_status` и тестах.
4. Обновить `TaskStatus` в `src/shared/api/database.types.ts`.
5. Обновить `src/shared/lib/task-status.ts`.
6. Обновить UI-тексты и README.
7. Обновить integration-тесты.
8. Применить миграцию на тестовом проекте, затем на production по процедуре ADR-010.

Миграция значений enum в PostgreSQL изменяет существующие строки; отдельный backfill не требуется. Перед применением сделать резервную копию и проверить на тестовом окружении.

### Frontend

- Компоненты не вызывают `supabase.rpc` напрямую; только через `features/tasks/api.ts`.
- UI показывает только переходы, доступные текущей роли, но сервер всё равно проверяет их.
- Для `in_review → needs_revision` форма комментария обязательна и на клиенте, и в RPC.
- Ошибки RPC показывать через общий обработчик ошибок, не терять код ошибки.
- После успешного перехода инвалидировать задачу, историю, список задач и список объектов (для счётчиков).
- Не выполнять optimistic update без тестов на откат.

### Тесты

Обязательные сценарии:

- все разрешённые переходы по цепочке;
- запрет пропуска статуса;
- запрет перехода не тем исполнителем;
- запрет manager переводить `new → in_progress`;
- запрет executor принимать задачу;
- запрет `in_review → accepted` без manager;
- обязательный комментарий при `in_review → needs_revision`;
- запрет перехода по удалённой задаче;
- запрет перехода по задаче удалённого объекта;
- прямой `UPDATE status` запрещён;
- анонимный пользователь не может вызвать RPC;
- история содержит корректные `from_status`, `to_status`, `comment`, `changed_by`.

## Validation

- Запустить integration-тесты `npm run test:security` при наличии `.env.test`.
- Проверить прямой `UPDATE tasks SET status = ...` для manager и executor.
- Проверить конкурентный сценарий: два перехода одной задачи одновременно; ровно один должен завершиться успешно.
- Проверить, что после возврата на доработку комментарий виден в истории.
- Проверить, что `accepted` не имеет исходящих переходов.
- Проверить, что UI не предлагает недоступные переходы.
- После миграции имён повторить все сценарии с каноническими именами.
