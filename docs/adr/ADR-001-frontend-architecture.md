# ADR-001: Frontend Architecture

- Status: Accepted
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Проект уже реализован как небольшое SPA: React 19, TypeScript strict, Vite, TanStack Query, React Router, React Hook Form, Zod, Supabase JS и Chakra UI v3. Требуется зафиксировать архитектурные границы, чтобы дальнейшая разработка не превратила приложение в набор связанных между собой компонентов и прямых запросов к Supabase.

Требования тестового задания предлагают FSD-подобную структуру (`app`, `pages`, `features`, `entities`, `shared`), но разрешают упрощение, если разделение создаёт лишнюю сложность. Текущий код уже близок к этой структуре, однако имеет отклонения:

- используется `entities/profile`, а не `entities/user`;
- каталог `app` плоский;
- нет `shared/config` и `shared/types`;
- доменные метаданные статусов находятся в `shared/lib/task-status.ts`;
- публичные `index.ts` у модулей отсутствуют.

Дополнительно требуется зафиксировать выбор UI-библиотеки: в проекте используется Chakra UI v3, тогда как тестовое задание упоминает shadcn/ui.

## Decision

Принять FSD-lite архитектуру без механического перекладывания существующего кода.

Слои:

- `src/app` — композиция приложения: providers, router, guards, layout. Без бизнес-логики и без запросов к Supabase.
- `src/pages` — маршрутные страницы. Композируют feature-хуки, entity-компоненты и shared-UI. Не вызывают Supabase напрямую.
- `src/features` — пользовательские сценарии: `auth`, `objects`, `tasks`. Содержат API-функции, query/mutation hooks, схемы валидации, формы и сценарные компоненты.
- `src/entities` — доменные типы и презентационные компоненты: `profile`, `object`, `task`. Без mutations, без доступа к Supabase и без импортов из `features`, `pages`, `app`.
- `src/shared` — инфраструктура и переиспользуемый UI: клиент Supabase, типы БД, общие компоненты, форматтеры, обработка ошибок. Без доменных сценариев.

Запрещены циклические зависимости и импорты во внутреннюю реализацию соседних модулей. Новый код должен использовать публичный API модуля через `index.ts`. Существующие глубокие импорты считаются унаследованными и мигрируют постепенно при изменении соответствующих файлов.

Принято сохранить Chakra UI v3. shadcn/ui не внедряется в рамках текущей архитектуры: это потребовало бы новых зависимостей, Tailwind и переписывания всех компонентов без выгоды для безопасности или бизнес-логики.

## Rationale

- Структура уже соответствует предметной области и не требует крупного рефакторинга.
- Разделение `features` и `entities` полезно: сценарии (создание задачи, смена статуса) отделены от презентационных карточек и доменных типов.
- Отказ от полного FSD с обязательными `index.ts`, `model/`, `lib/`, `ui/` внутри каждого модуля снижает бюрократию для приложения из нескольких экранов.
- Серверная бизнес-логика уже находится в PostgreSQL, поэтому клиентские слои должны оставаться тонкими.
- Chakra UI v3 уже используется во всех компонентах; смена UI-библиотеки не улучшает архитектуру и создаёт риск регрессий.

## Alternatives Considered

### Полный FSD с `entities/user`, подкаталогами `app/providers` и `app/router`, обязательными barrel-файлами

Отклонено: для текущего размера приложения это добавляет больше файлов и церемоний, чем даёт пользы. Переименование `profile` в `user` также создало бы расхождение с таблицей `profiles` и существующими типами.

### Плоская структура по типам файлов (`components/`, `hooks/`, `api/`)

Отклонено: при росте приложения такая структура хуже показывает границы доменов и провоцирует циклические зависимости.

### Только package-by-feature без `entities`

Отклонено: карточки объектов и задач, типы и бейджи статусов переиспользуются несколькими сценариями. Их размещение в одной из features создало бы нежелательные связи между features.

### Переход на shadcn/ui

Отклонено в рамках текущего решения: требует новых зависимостей, Tailwind, переписывания UI и не влияет на безопасность или корректность бизнес-логики. Вопрос может быть пересмотрен отдельным ADR.

### Перенос бизнес-логики статусов на клиент

Отклонено: клиентские проверки легко обойти. Источник истины — PostgreSQL, RPC и RLS.

## Consequences

Положительные:

- Понятное место для новых компонентов, API-функций и хуков.
- Снижение риска случайных связей между доменами.
- Возможность постепенно улучшать границы без большого переписывания.
- Сохраняется уже работающий UI и тесты.

Отрицательные:

- Часть существующих импортов идёт в конкретные файлы, а не в публичный API; это технический долг.
- `shared/lib/task-status.ts` содержит доменные метаданные и формально нарушает правило «shared не знает о домене».
- Нет автоматической проверки границ импортов; соблюдение пока контролируется ревью и договорённостью.
- Chakra UI v3 расходится с формулировкой тестового задания про shadcn/ui.

## Implementation Guidelines

### Целевая структура

```text
src/
  app/
    App.tsx
    AppLayout.tsx
    guards.tsx
    providers.tsx
    router.tsx
  pages/
  features/
    auth/
    objects/
    tasks/
  entities/
    profile/
    object/
    task/
  shared/
    api/
    ui/
    lib/
supabase/
  migrations/
  tests/
docs/
  adr/
```

Не создавать пустые `shared/config` и `shared/types`. Добавлять их только при появлении реального содержимого. Не разносить `app` на подкаталоги, пока в нём меньше 10–12 файлов или пока нет второй реализации router/providers.

### Разрешённые направления импортов

- `app` → `pages`, `features`, `entities`, `shared`.
- `pages` → `features`, `entities`, `shared`.
- `features/<name>` → `entities`, `shared`, файлы своей feature.
- `entities/<name>` → `shared`, файлы своей entity.
- `shared` → только `shared`.

Запрещено:

- `features/A` → `features/B`;
- `entities/A` → `features/B` или `entities/B` (кроме случаев, когда доменная связь оформлена через тип в `shared` или через prop);
- `pages` → `app`;
- любой импорт из `app` в нижележащие слои;
- циклические зависимости.

### Публичный API модулей

- Новый код импортирует feature/entity только через `index.ts` этого модуля.
- Внутри своего модуля разрешены прямые импорты файлов.
- Экспортировать через `index.ts` только то, что действительно является контрактом модуля.
- Не экспортировать внутренние helper-функции и детали реализации.
- Существующие прямые импорты (например, `@/features/tasks/hooks`) не ломать в этой задаче; при изменении файла мигрировать на публичный API.

### Где размещать код

- Новый сценарный компонент (форма, диалог, панель действий) — `src/features/<domain>/`.
- Переиспользуемая карточка или бейдж доменной сущности — `src/entities/<entity>/`.
- Общий UI без доменных знаний — `src/shared/ui/`.
- Запрос к Supabase — `src/features/<domain>/api.ts`.
- Query/mutation hook — `src/features/<domain>/hooks.ts`.
- Схема валидации — `src/features/<domain>/<name>.schema.ts`.
- Общий форматтер или обработчик ошибок — `src/shared/lib/`.
- Типы строк БД — `src/shared/api/database.types.ts`.
- Доменные типы, расширяющие строки БД, — `src/entities/<entity>/types.ts`.

### Именование

- Компоненты и файлы компонентов: `PascalCase`, например `TaskActions.tsx`.
- Хуки: `useXxx`, файл `hooks.ts` внутри feature.
- Query keys: `objectKeys`, `taskKeys`.
- Схемы: `*.schema.ts`, тип значений — `XxxValues`.
- API-функции: глагол + сущность, например `listMyTasks`, `transitionTaskStatus`.
- Типы: `XxxRow` для строк БД, `XxxWithRelations` для составных моделей.
- Не создавать файлы `index.ts` ради реэкспорта всего подряд.

### Работа с типами

- `TypeScript strict` обязателен.
- Не использовать `any` без письменного обоснования в PR/комментарии.
- Не использовать `@ts-ignore` для сокрытия ошибок.
- При необходимости сужения использовать `unknown` и явные type guards.
- Текущие касты `as unknown as TaskWithRelations` в API-слое считаются техническим долгом из-за ручных типов БД. Новые касты без обоснования запрещены.

### UI-библиотека

- Использовать Chakra UI v3 и `lucide-react`.
- Не добавлять shadcn/ui, Tailwind или другую UI-систему без отдельного ADR и согласования.
- Общие визуальные состояния (`LoadingState`, `ErrorState`, `EmptyState`, `ConfirmDialog`, `PageHeader`) размещать в `shared/ui`.

### Известные исключения

- `src/shared/lib/task-status.ts` содержит доменные метаданные и логику доступных переходов. Это временное исключение. Целевое место — `entities/task` или отдельный модуль доменной модели. Перенос выполнять отдельной задачей вместе с миграцией имён статусов.
- `src/features/auth/AuthProvider.tsx` напрямую работает с Supabase Auth и профилем. Это исключение описано в ADR-002 и ADR-003.

## Validation

- Проверить, что новые импорты не нарушают матрицу направлений.
- Проверить отсутствие циклов (визуально или через будущий dependency-cruiser/ESLint boundaries).
- Проверить, что новый компонент не вызывает Supabase напрямую.
- Проверить, что бизнес-правила статусов не продублированы на клиенте как источник истины.
- Запустить `npm run typecheck` и `npm run lint`.
- При изменении структуры обновить этот ADR и `AGENTS.md`.
