# ADR-009: Error Handling

- Status: Proposed
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Ошибки в приложении возникают из разных источников:

- Supabase Auth (`AuthError`);
- PostgREST (`PostgrestError` с `code`, `message`, `details`, `hint`);
- RPC (`transition_task_status` с кодами `42501`, `P0002`, `23514`, `23503`);
- сетевые ошибки;
- ошибки валидации Zod;
- ошибки рендера React.

Текущая реализация:

- `src/shared/lib/errors.ts` содержит `getErrorMessage` и карту точных сообщений/кодов;
- mutation hooks показывают ошибки через toaster;
- `ErrorState` показывает ошибку загрузки с кнопкой повтора;
- формы показывают ошибки полей через `Field.ErrorText`;
- `LoginForm` показывает серверную ошибку в `Alert`;
- некоторые компоненты ловят ошибку `mutateAsync` и игнорируют её, потому что toast уже показан хуком.

Чего нет:

- типизированной модели ошибок;
- централизованного логирования;
- React error boundary;
- стабильного маппинга кодов вместо точных английских сообщений;
- единого правила, какие ошибки можно показывать пользователю.

## Decision

Принять целевую модель обработки ошибок. Статус `Proposed`, потому что типизированные ошибки, error boundary и логирование ещё не реализованы. Текущий `getErrorMessage` считается baseline, который нужно постепенно заменить.

### Модель ошибки

Ввести тип `AppError`:

```ts
export type AppErrorCode =
  | 'AUTH_REQUIRED'
  | 'FORBIDDEN'
  | 'NOT_FOUND'
  | 'VALIDATION'
  | 'CONFLICT'
  | 'NETWORK'
  | 'UNKNOWN'

export type AppError = {
  code: AppErrorCode
  message: string
  userMessage: string
  cause?: unknown
}
```

Правила:

- `message` — техническое описание для логов, не для UI.
- `userMessage` — безопасное сообщение на русском.
- `cause` — исходная ошибка Supabase/network, не показывается пользователю.
- Не включать в ошибку токены, пароли, session, полные ответы Supabase.

### Маппинг

Использовать коды, а не точные строки сообщений:

- `42501` → `FORBIDDEN`;
- `P0002`, `PGRST116` → `NOT_FOUND`;
- `23503` → `NOT_FOUND` или `CONFLICT`;
- `23514` → `VALIDATION`;
- `23505` → `CONFLICT`;
- `AuthError` → `AUTH_REQUIRED`/`FORBIDDEN` в зависимости от контекста;
- network/fetch failure → `NETWORK`;
- всё остальное → `UNKNOWN`.

Точные английские сообщения можно оставить как fallback, но не как основной механизм.

### UI-состояния

- Ошибка query → `ErrorState` с кнопкой «Повторить».
- Ошибка mutation → toast с `userMessage`.
- Ошибка поля формы → `Field.ErrorText`.
- Ошибка входа → `Alert` в `LoginForm`.
- Недоступная или отсутствующая сущность → `EmptyState` («не найдено/недоступно»), без раскрытия факта существования чужих записей.
- Ошибка рендера → error boundary с безопасным экраном и возможностью вернуться.
- Не использовать `alert()`, `confirm()` и сырые `console.error` в production-коде.

### Логирование

- Не логировать пароли, токены, publishable/secret keys, session и персональные данные.
- В dev допустим структурированный лог ошибки без секретов.
- В production добавить централизованный logger только после выбора инструмента и согласования.
- Не отправлять в внешний сервис весь объект ошибки Supabase без фильтрации.

## Rationale

- Коды PostgREST стабильнее текстов сообщений.
- Типизированная ошибка упрощает обработку в hooks и UI.
- Разделение `message`/`userMessage` предотвращает утечку технических деталей.
- Error boundary защищает от полного падения приложения.
- Единые правила делают поведение предсказуемым.

## Alternatives Considered

### Оставить только `getErrorMessage`

Отклонено как долгосрочное решение: точные строки хрупкие, нет кодов и логирования. Текущий helper остаётся baseline до миграции.

### Показывать пользователю сырые сообщения Supabase

Отклонено: утечка технических деталей, непонятный язык, возможное раскрытие структуры БД.

### Глобальный store ошибок

Отклонено: ошибки локальны для запроса/формы; глобальный store усложнит жизненный цикл.

### Логировать всё в консоль

Отклонено: бесполезно в production и рискованно из-за секретов.

### Игнорировать ошибки в `catch`, потому что toast уже показан

Допустимо только с комментарием, объясняющим, что ошибка обработана mutation hook. Не использовать пустой `catch` без объяснения.

## Consequences

Положительные:

- Предсказуемые сообщения для пользователя.
- Меньше утечек технических деталей.
- Упрощается тестирование маппинга.
- Появляется основа для логирования и мониторинга.

Отрицательные:

- Требуется рефакторинг существующих мест обработки ошибок.
- Нужно поддерживать маппинг кодов при изменении RPC/БД.
- Логирование требует отдельного решения о хранении и приватности.
- Error boundary добавляет код, который нужно тестировать.

## Implementation Guidelines

### Файлы

- `src/shared/lib/errors.ts` — маппинг и `getErrorMessage`/`toAppError`.
- `src/shared/ui/ErrorState.tsx` — состояние ошибки загрузки.
- `src/shared/ui/toaster-store.ts` — toaster.
- `src/app/` — место для error boundary и router error element.
- Mutation hooks — показ toast и проброс `AppError`.

### Правила обработки

- API-функции не показывают UI и не логируют; они выбрасывают исходную ошибку.
- Hooks преобразуют ошибку в `AppError` и показывают toast.
- Компонент может ловить `mutateAsync`, чтобы закрыть диалог/предотвратить unhandled rejection, но не должен дублировать сообщение.
- Формы показывают ошибки полей; серверные ошибки — в общем Alert/toast.
- Не глотать ошибки без комментария.
- Для `ErrorState` всегда давать retry, если запрос можно повторить.
- Для auth-ошибок не показывать, существует ли email; использовать нейтральное «Неверный email или пароль».

### Error boundary

Добавить компонент error boundary (классовый или через router `errorElement`) на уровне приложения или layout. Требования:

- не показывать stack trace пользователю;
- предлагать вернуться на главную/повторить;
- логировать ошибку без секретов;
- не ломать навигацию.

### Supabase

Помнить, что `PostgrestError` и `AuthError` не всегда являются `instanceof Error`. Обрабатывать объекты с полями `message`, `code`, `details`, `hint` явно.

### RPC-коды

Для `transition_task_status`:

- `42501` — нет прав/не тот исполнитель/требуется авторизация;
- `P0002` — задача не найдена;
- `23514` — недопустимый переход, отсутствует комментарий, удалённая задача/объект;
- `23503` — объект не найден/удалён.

Сообщения должны быть понятны пользователю, но не раскрывать лишние детали.

## Validation

- Проверить, что ошибки query показываются через `ErrorState`.
- Проверить, что ошибки mutation показываются один раз.
- Проверить, что ошибки полей отображаются у соответствующих полей.
- Проверить, что сырые SQL-сообщения не попадают в UI.
- Проверить, что после ошибки рендера приложение не падает полностью (после внедрения boundary).
- Проверить, что в логах нет токенов, паролей и ключей.
- Добавить unit-тесты на маппинг кодов.
