# ADR-008: Testing Strategy

- Status: Proposed
- Date: 2026-11-05
- Decision Makers: Project Team

## Context

Сейчас в проекте есть один интеграционный набор тестов: `tests/security.test.mjs`. Он запускается через `node --test` и проверяет реальные RLS-политики, гранты и RPC против облачного Supabase.

Фактическое состояние:

- unit-тестов нет;
- component-тестов нет;
- SQL-тестов в `supabase/tests` нет;
- CI-конфигурации нет;
- тесты требуют `.env.test`, publishable key и трёх пользователей (manager, executor1, executor2);
- тесты создают собственные объекты и задачи и помечают их удалёнными после завершения;
- команда: `npm run test:security`.

Такой набор хорошо проверяет безопасность, но не подходит как единственный уровень тестирования: он медленный, зависит от сети и секретов, не покрывает чистые функции и UI-взаимодействия.

## Decision

Принять стратегию тестирования с несколькими уровнями. Статус `Proposed`, потому что unit/component/SQL-тесты и CI ещё не реализованы. Существующий `tests/security.test.mjs` считается обязательным baseline для изменений в RLS, RPC и бизнес-правилах.

### Уровни

1. **Unit-тесты** — чистые функции и схемы:
   - `getAvailableTransitions`;
   - метаданные статусов;
   - `getErrorMessage`;
   - Zod-схемы;
   - вспомогательные mapper-функции.
2. **Component-тесты** — формы и сценарии UI с замоканными API/hooks:
   - `LoginForm`;
   - `ObjectFormDialog`;
   - `TaskFormDialog`;
   - `TaskActions`;
   - состояния loading/error/empty.
3. **Integration-тесты** — реальный Supabase (локальный или отдельный тестовый проект):
   - RLS;
   - гранты;
   - RPC;
   - история;
   - multi-user сценарии.
4. **SQL-тесты** — проверки схемы, функций и триггеров в `supabase/tests`:
   - constraints;
   - RLS-политики;
   - `SECURITY DEFINER` и `search_path`;
   - запрет прямого изменения статуса;
   - неизменяемость истории.
5. **CI-проверки** — typecheck, lint, build; integration-тесты только при наличии безопасно настроенных секретов или локального Supabase.

### Инструменты

Текущий стек:

- `node:test` и `node:assert/strict`;
- `@supabase/supabase-js`;
- `dotenv`.

Предлагаемое развитие:

- для unit-тестов TypeScript предпочтителен Vitest или аналог, но добавление зависимости требует отдельного согласования;
- для component-тестов — Vitest + React Testing Library после согласования;
- для SQL — pgTAP или SQL-скрипты в `supabase/tests`;
- не добавлять тестовые зависимости без ADR/согласования.

До появления нового runner можно писать unit-тесты на чистом JavaScript для уже скомпилированных/простых модулей или тестировать логику через integration-тесты.

## Rationale

- Разные уровни тестов ловят разные классы ошибок: unit — логику, integration — RLS/RPC, component — взаимодействие.
- Существующие security-тесты — самый ценный актив проекта; их нельзя заменять моками.
- Реальные RLS-тесты обязательны, потому что безопасность нельзя проверить только по коду.
- Multi-user сценарии критичны: большинство утечек возникает между пользователями.
- CI предотвращает регрессии, но не должен требовать production-секретов.

## Alternatives Considered

### Оставить только integration-тесты

Отклонено: медленно, дорого, зависит от сети и не покрывает UI/чистые функции.

### Заменить integration-тесты моками Supabase

Отклонено: моки не проверяют реальные RLS-политики, гранты и триггеры. Это создаёт ложное чувство безопасности.

### Добавить Vitest и Testing Library немедленно

Отложено: задача документации не предполагает установку зависимостей. Решение о инструментах должно быть отдельным и согласованным.

### Тестировать только вручную

Отклонено: не воспроизводимо и не защищает от регрессий.

## Consequences

Положительные:

- Появляется план покрытия всех критичных уровней.
- Security-тесты сохраняются как обязательный барьер.
- CI сможет проверять сборку и типы без секретов.
- Multi-user сценарии становятся явными.

Отрицательные:

- Пока не реализованы unit/component/SQL-тесты и CI.
- Потребуется добавить тестовые зависимости и настроить окружение.
- Integration-тесты остаются дорогими и требуют управления тестовыми пользователями.
- Тестовые данные нужно изолировать и очищать.

## Implementation Guidelines

### Расположение

- Integration/RPC/RLS: `tests/security.test.mjs` и новые файлы `tests/*.test.mjs`.
- SQL-тесты: `supabase/tests/`.
- Unit-тесты: рядом с модулем или в `tests/unit/` после выбора runner.
- Component-тесты: рядом с компонентом или в `tests/components/` после выбора runner.

### Обязательные сценарии

При изменении бизнес-логики проверять:

- все разрешённые переходы статусов;
- запрещённые переходы и пропуск статусов;
- переход не тем исполнителем;
- manager не может брать задачу в работу;
- executor не может принимать задачу;
- обязательный комментарий при возврате на доработку;
- доступ к чужим задачам и объектам;
- executor не видит объект без своей задачи;
- manager видит все объекты, задачи и историю;
- прямое изменение `status` запрещено;
- `author_id` и `created_by` нельзя подделать;
- assignee обязан иметь роль `executor`;
- роль нельзя повысить через `profiles`;
- историю нельзя вставлять, изменять или удалять;
- soft-deleted задача/объект скрывается от executor и блокирует переходы;
- анонимный пользователь не имеет доступа;
- после logout кэш не показывает данные предыдущего пользователя.

### Тестовые данные

- Использовать уникальные имена/маркеры с timestamp.
- Создавать данные через manager.
- После теста помечать созданные задачи и объекты `is_deleted = true`.
- Не удалять чужие данные.
- Не использовать production-проект.
- Не коммитить `.env.test`, пароли и ключи.

### CI

Минимальный набор:

```bash
npm run typecheck
npm run lint
npm run build
```

Integration-тесты:

- запускать только в доверенном окружении;
- использовать отдельный тестовый Supabase-проект;
- хранить секреты в CI secret storage;
- не запускать с production-ключами;
- при отсутствии секретов явно сообщать, что тесты пропущены, а не считать их пройденными.

### Команды

```bash
npm run test:security
```

Для будущих unit/component-тестов добавить отдельные scripts после согласования инструментов.

## Validation

- Проверить, что изменения RLS/RPC сопровождаются integration-тестами.
- Проверить, что новые бизнес-правила покрыты позитивными и негативными сценариями.
- Проверить, что тесты не требуют production-секретов.
- Проверить, что тестовые данные очищаются.
- Проверить, что CI не пропускает typecheck/lint/build.
- Зафиксировать в PR, какие тесты не удалось запустить и почему.
