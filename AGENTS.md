# AGENTS.md

Руководство для AI-агентов и разработчиков проекта Construction CRM. Документ краткий; детали и обоснования — в ADR.

## Project Overview

Construction CRM — мини-CRM для строительной компании. Позволяет вести объекты, назначать задачи исполнителям, менять статусы и хранить историю изменений.

Стек:

- React 19 + TypeScript strict + Vite
- Chakra UI v3 + lucide-react
- TanStack Query
- React Router
- React Hook Form + Zod
- Supabase Auth + PostgreSQL + RLS

Основные сущности:

- `profiles` — пользователь и роль (`manager` / `executor`);
- `objects` — строительный объект;
- `tasks` — задача на объекте;
- `task_status_history` — append-only история статусов.

Роли:

- `manager` — управляет объектами и задачами, назначает исполнителей, принимает задачи и возвращает на доработку;
- `executor` — видит только свои задачи и связанные объекты, выполняет задачи и отправляет на проверку.

Статусы задачи:

- канонические по требованиям: `new`, `in_progress`, `in_review`, `accepted`, `needs_revision`;
- текущая реализация БД/кода: `new`, `in_progress`, `on_review`, `accepted`, `needs_rework`.

Не смешивать эти наборы. До отдельной миграции в коде и БД используются текущие значения; канонические имена — целевые. Миграция описана в [ADR-005](docs/adr/ADR-005-task-status-workflow.md).

UI реализован на Chakra UI v3. shadcn/ui и Tailwind в проекте отсутствуют; не добавлять их без отдельного ADR.

## Architecture

Используется FSD-lite:

```text
src/
  app/          композиция: providers, router, guards, layout
  pages/        маршрутные страницы
  features/     auth, objects, tasks: api, hooks, forms, actions
  entities/     profile, object, task: типы и презентационные компоненты
  shared/       api, ui, lib: инфраструктура и переиспользуемый UI
supabase/
  migrations/   схема, RLS, триггеры, RPC
  tests/        SQL/RLS-тесты (планируется)
docs/
  adr/          архитектурные решения
```

Направления импортов:

- `app` → `pages`, `features`, `entities`, `shared`;
- `pages` → `features`, `entities`, `shared`;
- `features/<name>` → `entities`, `shared`, файлы своей feature;
- `entities/<name>` → `shared`, файлы своей entity;
- `shared` → только `shared`.

Запрещено:

- `features/A` → `features/B`;
- `entities/A` → `features/B` или `entities/B`;
- `pages` → `app`;
- импорты из `app` в нижележащие слои;
- циклические зависимости;
- импорт во внутреннюю реализацию соседнего модуля.

Новый код импортирует feature/entity через публичный `index.ts`. Существующие глубокие импорты — унаследованный долг; мигрировать при изменении файлов.

Бизнес-логика статусов, прав и переходов находится в PostgreSQL. Клиент только отображает данные и вызывает разрешённые операции.

## Source of Truth

Приоритет источников:

1. Требования тестового задания.
2. Принятые ADR в `docs/adr/`.
3. Существующие контракты и тесты (особенно `tests/security.test.mjs`).
4. Текущая реализация.

При противоречии:

- не изменять бизнес-правила молча;
- явно указать конфликт в ответе/PR;
- предложить минимальное согласованное решение;
- при необходимости обновить ADR, тесты и документацию.

Текущие известные отклонения:

- имена статусов в коде/БД отличаются от требований (см. ADR-005);
- используется Chakra UI v3 вместо shadcn/ui (см. ADR-001);
- unit/component/SQL-тесты и CI ещё не реализованы (см. ADR-008);
- типизированные ошибки и error boundary ещё не реализованы (см. ADR-009);
- кэш TanStack Query не очищается при logout (см. ADR-002);
- публичные `index.ts` у модулей отсутствуют (см. ADR-001).

## Coding Standards

- TypeScript strict обязателен.
- Не использовать `any` без письменного обоснования.
- Не использовать `@ts-ignore` для сокрытия ошибок.
- Не создавать чрезмерно большие компоненты; выносить части и хуки.
- Не дублировать бизнес-логику между компонентами, hooks и SQL.
- Предпочитать композицию наследованию и копированию.
- Соблюдать границы модулей и направления импортов.
- Использовать понятные имена: `PascalCase` для компонентов, `camelCase` для функций, `useXxx` для хуков.
- Не добавлять зависимости без необходимости и согласования.
- Не оставлять `TODO`/`FIXME` без объяснения и задачи.
- Не логировать секреты, токены, пароли и персональные данные.

## React Rules

- Только функциональные компоненты.
- Серверное состояние — TanStack Query.
- Локальное состояние — `useState`, React Hook Form, контекст для auth.
- Не копировать данные Query в глобальный store.
- Не использовать `useEffect` для вычисляемого состояния.
- Не выполнять запросы к Supabase из JSX-компонентов.
- API-функции — в `features/<domain>/api.ts`, hooks — в `features/<domain>/hooks.ts`.
- Не выполнять `supabase.from(...)` в `pages`, `entities` и `shared/ui`.
- Исключение — `AuthProvider` для чтения auth-сессии и профиля; новый код не должен копировать этот паттерн.
- После mutations инвалидировать связанные query keys.
- При logout очищать кэш TanStack Query.
- Ошибки query показывать через `ErrorState`, ошибки mutation — через toaster, ошибки полей — через `Field.ErrorText`.

## Supabase Rules

- Все пользовательские запросы выполняются в контексте пользовательской сессии.
- RLS обязателен для таблиц с пользовательскими данными.
- UI-проверки не заменяют RLS.
- Нельзя напрямую менять статус задачи через `UPDATE`.
- Переходы выполняются только через RPC `transition_task_status`.
- История статусов неизменяема через клиентский API.
- Роли не могут редактироваться пользователями.
- `service_role` и другие секреты запрещены во frontend.
- Объекты и задачи удаляются мягко (`is_deleted = true`), без физического `DELETE`.
- Миграции — только в `supabase/migrations/`; не редактировать применённые миграции.
- `SECURITY DEFINER`-функции обязаны иметь фиксированный `search_path = public, pg_temp`.
- Не выдавать `ALL` на таблицы ролям `anon`/`authenticated`.
- Не выдавать `UPDATE` на `tasks.status`, `profiles.role`, `author_id`, `created_by`, `created_at`.
- Не логировать и не передавать клиенту секретные ключи.

## Security Rules

Запрещено:

- отключать RLS ради исправления ошибок;
- использовать `service_role` на клиенте;
- ослаблять политики без объяснения и ADR;
- изменять историю статусов напрямую;
- обходить серверные проверки через UI;
- хранить секреты в репозитории;
- доверять `user_id` или `role`, переданным клиентом, без серверной проверки;
- добавлять `VITE_`-переменные с `sb_secret_` или `service_role`;
- логировать токены, пароли и session;
- применять destructive-миграции на production без backup.

Если найдена уязвимость или конфликт требований — сообщить, не исправлять молча.

## File and Module Rules

- Новый сценарный компонент — `src/features/<domain>/`.
- Переиспользуемая доменная карточка/бейдж — `src/entities/<entity>/`.
- Общий UI без доменных знаний — `src/shared/ui/`.
- API-запрос — `src/features/<domain>/api.ts`.
- Query/mutation hooks — `src/features/<domain>/hooks.ts`.
- Схема валидации — `src/features/<domain>/<name>.schema.ts`.
- Общие утилиты — `src/shared/lib/`.
- Типы строк БД — `src/shared/api/database.types.ts`.
- Доменные типы — `src/entities/<entity>/types.ts`.
- Публичный API модуля — `index.ts` (для нового кода).
- Не создавать пустые `shared/config` и `shared/types`; добавлять по необходимости.
- Не создавать циклические зависимости.
- Не импортировать внутренние файлы другого модуля; использовать публичный API.

## Testing Requirements

При изменении бизнес-логики проверять:

- разрешённые переходы статусов;
- запрещённые переходы и пропуск статусов;
- доступ к чужим задачам и объектам;
- ограничения ролей;
- обязательный комментарий при возврате на доработку;
- неизменяемость истории;
- запрет прямого `UPDATE status`;
- запрет подделки `author_id`/`created_by`;
- роль assignee;
- soft delete и блокировку переходов;
- анонимный доступ;
- очистку кэша при смене пользователя.

Команды:

```bash
npm run typecheck
npm run lint
npm run build
npm run test:security
```

`test:security` требует `.env.test` и тестовый Supabase. Если тесты нельзя запустить, явно указать причину и какие проверки выполнены вместо них.

## Agent Workflow

Перед изменениями агент обязан:

1. Изучить затрагиваемые модули и существующие паттерны.
2. Прочитать связанные ADR из таблицы ниже.
3. Составить краткий план изменений.
4. Проверить влияние на безопасность, RLS и бизнес-логику.
5. Внести минимально необходимые изменения, не переписывая лишнее.
6. Запустить доступные проверки: typecheck, lint, build, тесты.
7. Сообщить о результате, рисках и ограничениях.

Дополнительно:

- не менять бизнес-правила без явного согласования;
- не добавлять зависимости без необходимости;
- не выполнять миграции без отдельного запроса;
- не коммитить секреты;
- не изменять исходный код в задачах, где требуется только документация.

## Definition of Done

Задача завершена, когда:

- функциональность соответствует требованиям;
- `npm run typecheck` проходит;
- `npm run build` успешен;
- `npm run lint` проходит;
- нет очевидных нарушений архитектуры и границ модулей;
- права доступа не ослаблены;
- тесты проходят либо указаны причины, почему их не удалось выполнить;
- документация обновлена при изменении архитектурных решений;
- в отчёте перечислены риски и ограничения.
